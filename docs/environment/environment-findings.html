Environment Findings — The Muse VM Sandbox & Environment A Emulation

What this VM's sandbox actually permits, how each limit was diagnosed, and the proven recipe for emulating a fresh Ubuntu 24.04 machine inside it.

Recorded 2026-11-07 by Musebot-Astro · Baseline: 2026-11-07 13:27 CST · Companion to docs/egm-adoption/ (§9, §14 decision 3) · Source record: Environment A smoke test, 2026-11-07

Verdict. A fresh Ubuntu 24.04 environment can be emulated inside this VM and provisioned to the EGM adoption strategy's §9.1 specification — verified end to end on 2026-11-07 (git 2.43.0, Python 3.12.3, venv with pytest 9.2.0 + PyYAML 6.0.3). The working route is chroot + bind mounts, not systemd-nspawn: the sandbox blocks nspawn's sysfs mount, and three further sandbox behaviours (below) each required a diagnosed workaround.

2. The three walls

Each wall was diagnosed by reproduction with minimal probes, not inferred from the first error message. Debootstrap's own report ("Tried to extract package, but tar failed") named none of them.

Wall 1 — Filesystem

The workspace volume refuses directory ownership changes

Symptom. debootstrap into ~/workspace died extracting the first package (base-files). Manual extraction isolated it: tar: ./var/local: Cannot change ownership to uid 0, gid 50: Operation not permitted.

Diagnosis. File chown succeeds for every probed uid/gid pair; directory chown fails (strace: fchownat(...) = -1 EPERM). The workspace mount is setgid root:nogroup (2770): new directories are forced to group nogroup (65534) with the setgid bit stripped, and their ownership cannot be changed afterwards. The same probes on the root overlay (/tmp, /root, /var/tmp) all succeed.

Workaround. Build root filesystems on the root overlay (e.g. /root/envA/rootfs), never under ~/workspace. Note the trade-off: paths outside the home volume do not survive VM replacement — rebuild from the recipe in §3 instead of relying on the artefact persisting.

Wall 2 — Containers

systemd-nspawn cannot boot; chroot + bind mounts can

Symptom. systemd-nspawn -D <rootfs> aborts: "Failed to mount sysfs … Operation not permitted". mknod is likewise blocked, so debootstrap leaves placeholder regular files in /dev.

Diagnosis. Bind mounts — including bind-mounting /proc and individual device files — are permitted. Only fresh mounts of pseudo-filesystems and device-node creation are refused.

Workaround. Enter the rootfs with chroot after bind-mounting /proc and the device files (null, zero, urandom, random, full, ptmx) over the placeholders. The userland and filesystem are genuinely fresh; the cost is isolation fidelity — the container shares the host's PID and UTS namespaces (no own hostname or init).

Wall 3 — Network

Chrooted processes get no HTTP through the egress proxy

Symptom. apt-get update inside the chroot fails every fetch ("Connection failed [IP: 198.18.149.67 3128]"), with or without proxy credentials, with retries, and with HTTP pipelining disabled.

Diagnosis. Bare TCP connections from inside the chroot succeed — to the proxy and directly to archive.ubuntu.com:80. A hand-written proxied HTTP GET from inside the chroot receives no response at all. The identical requests from host processes (debootstrap's downloads, host apt) succeed. The discriminator is the process context, not credentials, request shape, or reachability.

Workaround. Host-assisted fetching: run downloads from host processes into the rootfs (host apt for lists and .debs, host pip download for wheels), then install inside the chroot with networking switched off (apt-get --no-download, pip install --no-index). Consequence for any in-environment validation: operations that fetch from inside the environment (git clone, harness/plugin installs) hit this wall and must be staged from the host.

3. The proven recipe

# 1. Build the rootfs on the root overlay (wall 1), never under ~/workspace
debootstrap --variant=minbase noble /root/envA/rootfs http://archive.ubuntu.com/ubuntu/

# 2. Sources: minbase ships "noble main" only, but python3-venv lives in
#    universe. Write the standard deb822 source (all suites/components,
#    as a cloud image ships) to etc/apt/sources.list.d/ubuntu.sources
#    inside the rootfs and remove etc/apt/sources.list.

# 3. Runtime plumbing (wall 2)
cp /etc/resolv.conf /root/envA/rootfs/etc/resolv.conf
mount --bind /proc /root/envA/rootfs/proc
for d in null zero urandom random full ptmx; do
  touch /root/envA/rootfs/dev/$d
  mount --bind /dev/$d /root/envA/rootfs/dev/$d
done

# 4. Host-assisted fetch, in-chroot install (wall 3)
apt-get -o Dir=/root/envA/rootfs update
apt-get -o Dir=/root/envA/rootfs -y --download-only install git python3 python3-venv
chroot /root/envA/rootfs env DEBIAN_FRONTEND=noninteractive \
  apt-get -y --no-download install git python3 python3-venv

# 5. venv + pins from host-downloaded wheels
pip download pytest==9.2.0 PyYAML==6.0.3 -d /root/envA/rootfs/tmp/wheels   # on the host
chroot /root/envA/rootfs python3 -m venv /tmp/egm-venv
chroot /root/envA/rootfs /tmp/egm-venv/bin/pip install \
  --no-index --find-links /tmp/wheels pytest==9.2.0 PyYAML==6.0.3

# 6. Teardown: umount the binds (proc, dev/*)

5. Findings that feed back into the strategy document

  • §9.1 assumes a cloud image's apt sources. python3-venv is in noble universe; a bare minbase rootfs enables only main, so the doc's "install from the distro packages" step fails verbatim there. Cloud images enable universe by default, so §9.1 is correct for its stated target — but the assumption is worth one sentence in the document.
  • Phase 3 scope. Provisioning and §9.5's offline checks are executable in this environment today. The E2E fixture is not, without host-assisted staging: wall 3 blocks the in-environment fetches it needs (repository clone, harness install), and the harness sign-in remains a manual step regardless of environment.

Hazard — apt-get -o Dir= does not provision a rootfs

Dir= relocates apt's lists and cache only; dpkg still runs against the host. On 2026-11-07 an apt-get -o Dir=<rootfs> install installed the package set on the host and half-configured the host's tzdata: the host's /etc/timezone is a runtime-owned file (nobody:nogroup) that guest root cannot write, so the postinst's unconditional write fails. Repair: bind-mount a writable copy over /etc/timezone, then dpkg --configure -a — host audit clean afterwards. Always pair Dir= with --download-only and install inside the chroot, per the recipe.

6. Deltas vs a true fresh VM

  • Shared kernel; chroot shares the host PID/UTS namespaces (no own hostname, no init).
  • In-environment HTTP egress is impaired (wall 3); provisioning is host-assisted.
  • Egress traverses this environment's proxy and its domain rules; a cloud VM's would not.
  • Directory ownership inside the rootfs is normal — wall 1 applies to the workspace volume only.
