OpenShell Patterns — Adoption Plan for AEP

AEP vendored repo maintenance lane · Author: Musebot-Astro · Date: 2026-11-13 · Status: plan from a completed adversarial panel — nothing in this document has been executed
Basis: pattern inventory and four-lens panel record in files/openshell-patterns/. The OpenShell product itself remains DEFER per the companion evaluation; this plan concerns only its ideas, re-implemented minimally in AEP's own shape.

Executive takeaway

An adversarial panel — security, architecture, environment, and cost lenses, each attacking fit rather than summarising — tested twelve OpenShell patterns against AEP's architecture, its actual environments, and its existing mechanisms. Eight do not survive. Several are already present in AEP under other names: ESF's provider abstraction, the branch-and-PR lifecycle, the ghg ledger. Two are category errors for a fleet of agent sessions rather than containerised workloads. And the flagship mechanisms — the credential broker, the runtime supervisor, the egress fence — form a chain whose load-bearing link, a buildable network fence, does not exist in AEP's sandbox; adopting them there would manufacture polished governance records for a boundary that is not physically present. Four adaptations survive, all small, all one-shot tools, none requiring a resident process: a power-differ for policy-affecting pull requests, per-run scoped credentials inside ESF, wiring the already-built boot gate into every autonomous launch path, and a generated read-only index of AEP's federated authority surfaces. The plan's shape: a test-first battery (Phase 0, roughly a day and a half) gates four small builds across three further phases (an estimated 7–13 agent-days in total if every test passes), each phase independently valuable, each with a named kill condition.

1. What the panel closed — and the only ways back in

These patterns are not in the plan. They are listed so their absence is a decision, not an omission. Re-examination happens only on the named trigger, through a fresh review — never by drift.

2. Phase 0 — The test battery (gates everything; ≈1.5 agent-days total)

No building happens in Phase 0. Four cheap experiments, each with a pre-registered pass/kill criterion, decide whether the corresponding build exists at all. A killed item closes with a dated note in the panel record — that is a successful outcome of this phase, not a failure of the plan. One informational item rides along: a two-hour credential census (which providers' credentials agents actually use, at what scope), whose only consumer is the P1 watch trigger in §1.

Phase 0 is independently valuable: it converts four plausible investments into four verified decisions for ~1.5 days, and its census artefacts (launch paths, credential inventory) are durable AEP documentation in their own right.

3. Phase 1 — The power-differ (P2, adapted)

What AEP builds

  • A check_policy_delta.py in the existing scripts/ verifier family, alongside mechanical_verify.py — a batch tool, no daemon, no new language.
  • Inputs are the policy-bearing artefacts AEP already diffs by eye: policy.data, ghg's cap/bucket tables, and skill manifests/frontmatter. One differ per artefact type, reporting into a single machine-generated PR comment: "Newly allowed: … / Newly denied: …".
  • A CI check that fails closed until a human acknowledges the delta on the PR — acknowledgement is a recorded human act, never an approval substitute and never auto-satisfied by the tool itself.
  • A standard proposal block for policy-affecting PR descriptions (newly allowed / why / expiry) — the surviving residue of P3, riding at zero marginal cost.

Entry gate and proof

Entry gate is G-P2. The build's own acceptance proof is the same replay, re-run against the finished tool in CI form: seeds caught, and the delta comment present and correct on a synthetic policy-affecting PR. Estimated build: 2–4 agent-days; carrying cost dominated by upkeep of the artefact-boundary definitions, inside the package ceiling in §6.

What AEP explicitly does not take from OpenShell

  • The claim and the name "formally verified." The differ computes a delta over a stated model of each artefact; it does not verify an implementation, reachability through allowed hosts, or data-level exfiltration over allowed methods — and its output must say what its model covers.
  • A new policy language (YAML/Cedar) or a standalone prover product. AEP's policy stays where it lives; the differ adapts to the artefacts, not the reverse.
  • Auto-approval semantics. In OpenShell the prover gates auto-approval; in AEP nothing auto-approves — the differ informs the human gate that already exists.

Phase 1 is independently valuable: it is the panel's one conceded capability gap, and if the plan stops here, AEP keeps the single highest-leverage artefact of the four.

4. Phase 2 — Execution-path gap closures (P7 and P6, adapted; independent of each other)

4a. Per-run scoped credentials for ESF runs (P7)

  • Builds: in ESF's harness credential path — credentials for a run are scoped to that run's needs, bound to the run as their generation, and expired at run end. Implementation reuses the shapes AEP already operates (ghg's lease/reservation machinery; ESF run create/destroy as the generation boundary). Estimated 3–6 agent-days, a few hundred lines, no new issuer service, no resident process.
  • Entry gate and proof: gate G-P7. Acceptance proof: the replay probe becomes a regression test — a credential from a finished run demonstrably fails, and an in-run credential demonstrably lacks scope beyond the run's harness needs.
  • Not taken: the gateway JWT pair architecture, supervisor-side token renewal, and any fleet-wide token infrastructure. GitHub is explicitly out of scope: ghg's posture (the agent never receives a token at all) is strictly stronger than short-lived tokens, and P7 must not be used to "harmonise" it downward.

4b. Boot-gate invocation wiring (P6)

  • Builds: wiring only. Every autonomous launch path enumerated by the census invokes the existing boot-gate.sh before work starts; the census result is checked in as the coverage record, and a lightweight check keeps new launch paths from silently bypassing it. Estimated 1–3 agent-days, no new mechanism.
  • Entry gate and proof: gate G-P6. Acceptance proof: re-run the census against the wired tree — 100% invocation coverage, demonstrated path by path.
  • Not taken: the freeze/terminate half of the pattern, in full. There is no supervisor link to monitor, one-shot runs have nothing to freeze, and on this VM the likeliest freeze trigger would be routine memory-balloon pressure — the gate would terminate healthy work. Fail-closed applies at startup, where AEP can honour it, and nowhere it would be theatre.

Phase 2 is independently valuable: each half closes a gap the panel verified exists today (standing in-run credentials; a built gate with unproven invocation) using only mechanisms AEP already owns.

5. Phase 3 — The authority index (P11, adapted as a view)

What AEP builds

  • A generator in the check_*.py family (~200 lines) that produces a read-only index page from the incumbent sources themselves: each authority surface (harness permissions, GitHub branch protection, ghg caps, policy.data, per-skill governance, procedural standing rules), its owner, its change path, and where it is enforced. Regenerated in CI; never hand-edited, so it cannot silently drift — when it is wrong, the generator is wrong in one fixable place.
  • The page carries a standing header: descriptive, not authoritative — the surfaces listed are the authority; this page is a map.

Entry gate and proof

Entry gate is G-P11. Acceptance proof: regenerate from a deliberately perturbed source (a renamed surface in a scratch copy) and show the index follows the source, not a stored copy. Estimated build: 1–3 agent-days; carrying cost ~zero by construction.

What AEP explicitly does not take from OpenShell

  • The ceiling itself: no consolidated policy store, no migration of any authority into a single document, no enforcement role for the index. AEP's authority stays deliberately federated — including the procedural rules (per-PR merge authorisation; the deletion rule's confirmation, one-hour delay, and reconfirmation) that do not survive translation into declarative predicates and are listed in the index as procedural, not rewritten.
  • The word "ceiling," and any completeness claim. The index enumerates known surfaces to speed up audits; it does not assert that the enumeration is the whole of the fleet's power.

Phase 3 is independently valuable: it pays only at audit and onboarding moments, which is exactly the frequency its near-zero carrying cost is priced for.

6. Risks and controls

R-A — The differ's output is trusted beyond its model

A machine-generated "newly allowed" list invites the same failure the panel identified in OpenShell's prover: reviewers downgrade their own scrutiny in proportion to a guarantee the tool does not provide. The differ is blind to reachability through allowed hosts, to exfiltration over allowed methods, and to cumulative creep across individually benign changes.
  • Control 1: Every delta comment carries its model scope in-line (which artefacts, which surfaces are not modelled), and the naming prohibition stands: the tool is a differ, never a verifier, in code, docs, and PR text.
  • Control 2: The differ also reports a trailing-window aggregate (power added across the last N policy-affecting merges), so salami-sliced escalation is visible as a sum, not only as benign individual deltas; the human acknowledgement requirement is not waivable by the tool.

R-B — ESF credential scoping breaks real runs

Per-run expiry and scoping touch the execution path: an over-tight scope or an expiry edge case (long runs, clock skew) can fail factory runs environmentally, in a VM where suites already fail below ~512 MB available memory and failure classification is costly.
  • Control 1: Roll out on one harness first, with the G-P7 replay probe wired as a pre/post regression pair; any run failure during rollout is classified baseline-first (pristine comparison) before it is attributed to the change.
  • Control 2: Scope is bound to run lifetime plus a stated grace window, and expiry events are logged as evidence in the run record — a credential dying mid-run must be diagnosable from the record, never a silent 401.

R-C — The index is mistaken for authority, or rots into shelfware

A tidy one-page map of "what the fleet can do" is exactly the kind of artefact that gets cited instead of the surfaces it maps — the completeness-theatre failure — or, at the other extreme, is generated once and never read.
  • Control 1: Generated-only, enforced mechanically: the page is a CI artefact with a regeneration check, carries the descriptive-not-authoritative header, and links every row to its living source rather than restating its contents.
  • Control 2: The G-P11 time-to-answer test is re-run at the first quarterly posture audit; if the index no longer measurably helps, it is deleted rather than maintained on momentum — the generator is small enough that deletion is cheap.

R-D — Scope creep back toward the platform

Each adaptation sits one rhetorical step from its rejected parent ("while we have a differ, why not a prover service?"; "while we scope ESF credentials, why not a broker?"). The rejected stack was priced by the panel at months of build, a resident footprint that does not fit this VM, and a perpetual dual-maintenance charge on owner attention — re-entering it piecemeal forfeits the panel's work.
  • Control 1: The standing constraints in §1 are plan-level gates, not guidance: any phase design that introduces a resident process, a new service, or an artefact describing an unbuildable boundary stops that phase automatically and returns to the owner as a new proposal.
  • Control 2: Re-entry to any rejected pattern happens only through its §1 named trigger plus a fresh panel — the triggers are the complete list; "we're already nearby" is not one of them.

R-E — The package's carrying cost quietly exceeds its budget

Four small tools are still four tools: boundary definitions drift, artefact formats change, and the weekly sweep inherits the attention cost — levied on the scarcest resource in the system, the owner's review time.
  • Control 1: A package ceiling of ~2 hours/month total carrying cost, observed at the weekly sweep; any component that exceeds its share twice running is a candidate for deletion, with deletion preferred over repair for the index and the wiring check.
  • Control 2: Every build lands as a single-purpose one-shot tool in an existing family (scripts/ verifiers, check_*.py, ESF harness path) with its gate test checked in beside it — no component may introduce a new runtime, framework, or configuration surface of its own.

7. Stop conditions and sequencing summary

  • Stop at any gate: a killed gate closes its pattern with a note; the plan continues with whatever survived. Zero surviving builds after Phase 0 is a valid, cheap endpoint (~1.5 days spent, four decisions verified).
  • Stop on physics: any design step that requires a resident process, a database, or memory headroom this VM does not have terminates that phase (see R-D Control 1).
  • Stop on attention: if the §6 R-E ceiling is breached by the package as built, the newest component is removed first — last in, first out — rather than letting the sweep absorb the growth.
  • Sequencing: Phase 0 → Phase 1 (differ) → Phase 2 (ESF credentials; boot-gate wiring — either order, independently) → Phase 3 (index). No phase depends on a later one; each phase's gate is re-checked at its start, not inherited from Phase 0 if time has passed.
