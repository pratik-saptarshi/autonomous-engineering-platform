1. Executive summary

The OpenCode installation in this VM has grown from a trial CLI install (2026-11-12) into a load-bearing part of the engineering environment: it is the execution plane for the OpenCode–OpenChamber bridge, carries the full live skills library, and is fronted by an OpenChamber control room. Its state is currently recorded only in scattered operational notes (TOOLS.md, lane memory files, a bridge runbook in a goal workspace). This plan produces a single, professional, verified documentation set in this repository that describes the setup as it actually is — installation, configuration, provider and model governance, the background-service API route, OpenChamber, and the bridge — together with the operations knowledge needed to recover it after a VM replacement. Every factual claim in the deliverables must be re-verified live at writing time; nothing is copied from notes on trust.

2. Objective and scope

Objective: an engineer (or agent) with no prior context can, from the documentation alone, understand, verify, operate, and rebuild the OpenCode setup in this VM.

In scope: the OpenCode CLI and its configuration; provider authentication state (existence, never values); the model catalog and the bridge allowlist; skills/MCP/agents/commands wiring; the background service and its API route; OpenChamber in external-attach mode; the bridge dispatcher and its operating rules; environment constraints of this VM that affect the setup; recovery procedures.

Out of scope: changing the setup itself (no installs, upgrades, config edits, or new provider connections); adopting the bridge beyond its current pilot status; documenting any credential value; the OpenChamber Space UI internals (covered by its own goal records).

5. Method and quality gates

  • Verify, don't transcribe. Every version, count, path, and state claim in the deliverables is produced by a named command run at writing time, with its output recorded in the task ledger. The §3 inventory is the starting hypothesis, not a source.
  • Secrets discipline. No credential values, no password-file contents, no API keys in any document, commit, or screenshot. A secrets scan is part of the hygiene gate.
  • Hygiene. scrubbing-public-tree over the branch's changed files before push (this is a public repo: no machine paths beyond what the setup itself requires, no agent headers, no process debris).
  • Independent review. A fresh reviewer checks the whole branch diff against this plan: factual accuracy against live re-runs, completeness against §4, no out-of-scope setup changes.
  • Repo gates. PR targets develop; CI green and zero unresolved review threads before the merge decision, which remains Pratik's per-PR call.
