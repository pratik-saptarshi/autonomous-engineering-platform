Executive takeaway

Named honestly, this plan adopts three things from Craft Anything: the Study tooling surface as a pinned reference (the engine's inspection-tool taxonomy and source, vendored under AEP's sha256 vendor-integrity regime), its evidence-record discipline (records carrying confidence, coverage, and limitations, consumed summary-first), and its clean-room posture as governed process. It does not adopt upstream's Check: verification in upstream operates on Build artifacts (rebuild_check, website build comparison, game self-test) and is semantically coupled to the Build harness, which remains out of scope — so the protocol's verification step is an AEP-side claim-verification process run against REA/Ghidra evidence, explicitly not upstream's Check. The v1 draft deferred the runtime on a false premise: upstream has in fact published five binary releases (v0.1.0, 2026-10-31, through v0.5.0, 2026-11-06) with Linux x86_64 packages, so the trigger Pratik named for D1 fired before he ruled, and Gate 0 puts the runtime posture back to him as an informed choice — a deliberate hold, or a re-scope that evaluates the published Linux packages early. The honest day-one delta after full execution is posture, discipline, and routing over the REA/Ghidra capability AEP already has, plus a pinned Study-surface reference — not a new engine. Footprint is ~13.6 MB and 4–5 PRs, and fully reversible under the exit criteria in Phase 2.

Risks and mitigations

RiskMitigations (≥2 each)
Premise falsity. This plan's v1 was drafted against stale README prose ("pre-first-release") that the Releases endpoint flatly contradicted — the deferral, D1's basis, and the footprint all inherited the error. Any future trigger, deferral, or maturity claim in this adoption can fail the same way. (1) Standing lesson, encoded: any deferral/trigger/maturity claim is verified against the GitHub Releases endpoint — the authority — never against README prose. Gate 0's grounding was re-verified that way. (2) Load-bearing facts in this plan name their verification source; any runtime-phase plan re-verifies release state at its own plan time instead of inheriting this document's numbers.
Instruction-surface import. The snapshot imports the fork's own AGENTS.md, CLAUDE.md, .githooks/, .coderabbit.yaml, and .github/ — agent/automation instructions that could be mistaken for AEP's own, or picked up by tooling run inside the tree. (1) Phase 1's disposition step strips or quarantines each surface with a rationale in PROVENANCE.md, before manifest generation; the removed/retained lists are shown in the snapshot PR. (2) The snapshot lives under reference/ as data and is never executed in place; the vendor-integrity manifest makes any later change to it a visible, reviewable diff.
Dependabot / vendor-integrity desync. Dependency tooling touching a vendored tree rewrites files the manifest pins, failing vendor-integrity CI (precedent: this repo's PR #93 experience with vendored trees). (1) Dependabot/dependency-alert scoping for reference/craft-anything/ is decided and recorded in the snapshot PR body before merge. (2) Pin regeneration is a single scripted step against the final tree, rehearsed locally before the PR — a desync is fixed by re-running the step, never by hand-editing hashes.
Posture leakage. D5's clean-room default is, mechanically, prose in a skill: an agent could still run Ghidra or a Deep inspection against a target whose inspection rights were never established. (1) The routing table binds posture to tool — Ghidra or engine-Deep on a target without an established right is out-of-protocol — and the claim-verification step checks the work record for the right and its basis before findings are reported. (2) The skill states the guarantee is advisory until a mechanical control exists, and the status-language rule ("protocol adopted; engine not installed") prevents reporting from overstating what the posture enforces.
Staleness economics. The fork is 246 commits behind and upstream ships roughly weekly; pinning without syncing pins a v0.3.0-era tree (upstream is already at v0.5.0), and every re-pin is a ~565–621-file PR with manifest churn. (1) Staleness budget with teeth: a re-pin or a recorded keep-decision is required when upstream moves >2 releases past the pin; D2 names the cadence and the owner. (2) The economics are stated honestly up front: nothing in AEP builds against the snapshot, so staleness degrades reference value only — and the Phase 2 exit criteria define when the snapshot stops earning its keep and is removed instead of refreshed.
Sunk-cost / museum precedent. A snapshot plus a protocol for an uninstalled engine can become a museum exhibit — kept because it was adopted, and cited by later lanes as precedent for adopting more unusable capability. (1) Adoption exit criteria with a named removal owner (Phase 2) make removal a governed, expected outcome rather than an admission of failure. (2) The status-language rule keeps the record honest ("protocol adopted; engine not installed"), so the adoption cannot be cited as a capability precedent it never was.
Sandbox constraint on any runtime phase. podman exec is blocked in this environment (mount-namespace setns denied) and network namespaces are host-only; the engine's Study mode runs target apps, so a containerized runtime cannot be operated the obvious way. (1) Any runtime phase — Branch B evaluation or a Phase 4 plan — must present the exec-free container answer (one-shot runs, state in volumes) or run natively on the VM; the choice is made in that phase's own plan, not assumed here. (2) Branch B's smoke test is specified against the published packages on the VM, not in a container, so the evaluation itself is never blocked by the sandbox.
Stand-in-tested tools. Some engine tools are tested only against stand-ins; the protocol could inherit unearned confidence in their outputs (and, under Branch B, in smoke-test results). (1) The protocol requires every evidence record to carry its limitations field verbatim — a record without stated limitations is treated as incomplete, not as strong. (2) The AEP-side claim-verification step cross-verifies load-bearing claims against an independent source (REA record or Ghidra output) before they are reported as findings.
Scope creep into Build or Check. The adoption drifts into driving the engine, its builder, or its build-comparison machinery — recreating the overlap the verdict excluded, now including Check, which v1 mislabeled as adopted. (1) The scope table names Build and Check as OUT with the coupling reason stated; the protocol's verification step is defined as a different artifact (AEP-side claim-verification). (2) The recurring CI routing check (Phase 3) plus Phase 2's stop condition return the boundary question to Pratik instead of letting an implementer improvise it.
Branding / license slip. The snapshot carries ArtCraft brand assets the license excludes; redistributing them as-is breaches the fork terms. (1) Disposition precedes manifest generation, so the strip is structural: stripping after manifest generation would fail the CI completeness check, not slip through silently. (2) PROVENANCE.md records the license, the brand exclusion, the exact strip list, and the nominative-use basis for the names retained in docs and the skill name.
Routing confusion. Three RE surfaces with overlapping claims (REA vs protocol for JS/Electron; protocol vs Ghidra for native) produce duplicated or contradictory analyses. (1) One routing table, quoted identically in both skills, with the protocol row's predicate made disjoint (clean-room required, or recreation-oriented deliverable — nothing else routes there). (2) One-evidence-record-per-question dedup rule, with REA named producer of record for JS/Electron and Ghidra for native deep work; the table is revisited only inside an authorized runtime plan.
