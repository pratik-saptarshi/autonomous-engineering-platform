Fork fleet tracking sheet + census batch — plan

AEP vendored repo maintenance lane · Author: Musebot-Astro · Date: 2026-11-18 · Status: plan only — no sheet created, no code written, no repo changed
Owner request (2026-11-18): "start maintaining a google sheet, for each fork repo, its upstream branch, sync status on upstream default to branch of same name, develop sync status and last updated by 'bot name'. We want to create a batch job and add it to AEP."

Executive takeaway

The fleet's standing record is currently re-derived from the daily sync's text log — and that record has already been caught wrong: for orca the log said 0 commits of develop lag, the 2026-11-16 fleet plan said 1,658, and a direct compare said 258. A tracking sheet is only worth keeping if every figure in it comes from a live compare taken at census time, so this plan builds exactly that: a read-only census script in AEP's scripts/ family that reuses fork-sync's discovery and compare pattern, emits a JSON census with an explicit unknown state (never a silent zero), and a nightly agent-run batch — after the 19:00 sync — that diffs the census against a Google Sheet and writes only the rows that changed, in machine-owned columns only, leaving a human annotation zone untouched. Attribution ("last updated by") uses a closed vocabulary of bot actors and admits unknown (external change) where no bot action is recorded, rather than guessing. Recommended shape: one spreadsheet, two tabs, one new AEP script with tests, one local cron in the existing fork-sync pattern — phased P0–P3 with a fixture-checked first census, and the Monday sweep re-pointed at the sheet only as a separately approved follow-up.

1. Grounding — what exists today

  • fork-sync.py (lane script, run nightly by cron as fork-upstream-sync-daily, GHG_ACTOR=fork-sync) discovers eligible forks — isFork AND default branch develop — then per fork makes three ghg calls: repo info (whose parent block names the upstream repo and its default branch, which is the fork's mirror branch name), a mirror-vs-upstream compare, and a mirror-vs-develop compare. It classifies mirrors as SYNC-NOOP / SYNC-FF / BLOCKED / SKIP and prints human-readable text to a log. It never modifies develop.
  • The measurement lesson (2026-11-17/18, verified live). Figures parsed from that text log are unreliable — compare direction and timing produced 0 vs 1,658 vs 258 for the same repo within two days, with no forward-merge in between. Direct compares taken at census time are the only trustworthy source. This plan therefore forbids log parsing for every figure in the sheet; the log is used for exactly one metadata purpose (sync attribution, §3) and even that gets a cleaner replacement in P1.
  • The 2026-11-16 fleet plan (Eng — AEP / Defense Factory lane) categorised the fleet from a log parse: (a1) 67 clean repos, (a2) 8 fork-local, (b) 5 blocked/missing mirrors, 64 no-action, with esf, docs-mcp-server, harness2, install and NeuroStrata excluded from bulk handling. This sheet supersedes that plan's category (a) census as the standing record; the plan's procedures and sequencing are unaffected.
  • Google Sheets connector. All Sheets access goes through the agent-mediated wrapper (hatch_gws_cli sheets …); authentication stays inside the wrapper and credential files are forbidden. A scheduled agent run can use it; a bare script cannot hold Google OAuth. This single fact decides the write-path design in §4.

2. Sheet design

One new spreadsheet, created under the owner's Google account via the connector, working title "Fork fleet — sync status" (Decision D1). Two tabs:

  • Fleet status — one row per eligible fork (~147), stable alphabetical order by fork repo, header row frozen, filter enabled. The batch never re-sorts: the owner sorts/filters ad hoc in the UI, and stable row positions are what make the human annotation zone safe (§2.2).
  • Summary — fully machine-owned, rewritten each run: census timestamp, counts by mirror/develop status, the blocked list, top develop lags, and the definitions of every status and of the attribution column. This is the blocked-first view, so the data tab doesn't need severity ordering.

2.2 Human zone, ordering, and write mechanics

  • Human-owned columns Q:R — Owner notes and Decision. The batch never writes Q:R, never clears them, and never moves them: rows are never re-sorted or deleted by the batch, so an annotation stays attached to its fork. Any future need to reorder is a manual, owner-side operation.
  • Diff-update, not full rewrite. Each run: read the machine range once, diff against the census by row key, and write only changed rows (one values batchUpdate with per-row ranges), plus the single-column O update for all verified rows and the Summary tab rewrite. Rationale: 147 rows is small enough that a full rewrite would be cheap in API terms, but a full rewrite would churn every cell nightly, erase the meaning of "last updated", and widen the window for clobbering a concurrent human edit inside the machine range. Diff-update makes a no-change re-run produce no state writes at all (idempotency, §4.3).
  • RAW values. All writes use valueInputOption=RAW; timestamps are ISO 8601 text (America/Chicago offset), counts are plain integers, SHAs literal — Sheets never re-interprets a value.
  • Read-back verification. After writing, the batch reads back the written ranges and the Summary timestamp before reporting success (the connector's own rule: an accepted write is not proof the sheet reads correctly).
  • Ownership & discoverability. The spreadsheet lives in the owner's Google account; its ID and link are recorded in the lane MEMORY.md and in an AEP doc page added by the build PR, so the sheet is findable from both sides.

3. Attribution — what "last updated by" can honestly mean

The column records the automation identity (GHG_ACTOR) responsible for the last state change a row reflects. What is knowable, stated plainly:

  • Mirror movements are attributable. fork-sync is the only automation that moves mirrors, and it runs as GHG_ACTOR=fork-sync. When a row's mirror SHA advances and the sync run record shows an APPLIED sync for that repo, the change is stamped fork-sync and column M takes that run's timestamp. To make this robust, P1 adds a small machine-readable run record to fork-sync (a JSON sibling of the text log: run timestamp, actor, per-repo applied list). Until that lands, the batch reads the same facts from the log's APPLIED lines and run headers — attribution metadata only, never figures.
  • Develop movements are not bot-made today. No automation merges into develop; the fleet plan's forward-merges will be human-approved, per-action events. A develop SHA that changes between censuses with no recorded bot action is stamped unknown (external change). The batch deliberately does not infer a person from commit authorship: the pusher of a merge is not recoverable from the compare API, and author ≠ actor for bot-assisted merges. Guessing a name would make the column a false record.
  • Convention going forward. Any future automation that moves a tracked branch must run under a named GHG_ACTOR and leave a run record; the census then attributes from that record. This is stated in the Summary tab so the column's semantics are printed next to its data.
  • First-observation rows (new fork, or a row whose prior state is unavailable) are stamped fork-fleet-census — the census is the actor that brought the row into the record, which is the only claim being made.

4. Batch job design

4.1 Shape: an AEP script + a local cron agent run

  • Script: scripts/fork_fleet_census.py in AEP, alongside check_policy_delta.py and mechanical_verify.py — stdlib-only, batch, no daemon. It performs discovery and all compares through ghg, and emits a census JSON (full SHAs, raw counts, per-repo status, error classes) plus a run summary. CLI in the family pattern: a default census mode writing the JSON to a named output path, and a --check mode that validates a census file against the schema (used by tests and by the agent run before any sheet write).
  • Exit codes: 0 = census complete (rows marked unknown are reported in the summary but do not fail the run); 1 = partial census (the repo list or a whole compare class failed — sheet is still updated for the repos that did measure, with the rest carried as unknown); 2 = fatal (ghg budget denial / gateway failure / repo list failure — no sheet write occurs). A ghg exit 75 anywhere stops the run at that stage and is reported as a budget denial, per the standing gateway rule — never retried around, never bypassed.
  • Runner: local cron, not GitHub Actions. A nightly cron job (fork-fleet-census-nightly) in the same pattern as fork-upstream-sync-daily, running as an agent job with GHG_ACTOR=fork-fleet-census, delivering its report to the AEP vendored repo maintenance chat. Actions is rejected for three reasons: every GitHub call must go through the local ghg gateway and its budget accounting (Actions would bypass it); the fleet compares need the gateway for the same reason; and Google write access from Actions would require a stored Google credential, against the vault posture (§4.2). Nothing about the job needs PR-triggered or in-repo execution.
  • Cadence & ordering: nightly at ~19:45 America/Chicago, after the 19:00 daily sync has finished, so mirror columns reflect post-sync state and column M/N attribution lines up with that evening's sync record. The census measures live state whenever it runs, so a missed or denied sync does not corrupt it — the sheet simply shows the pre-sync figures with that night's verification timestamp. The Monday weekly sweep re-pointing at the sheet is recommended but is a separate follow-up task (it rewrites the sweep's instructions), not part of this build (Decision D4).

4.2 Google write path — agent-mediated, by design

The Sheets connector is agent-mediated: its wrapper holds authentication internally and credential files are forbidden. A bare script therefore cannot write to Sheets, and this plan does not try to make it one. The nightly agent run is the writer:

  1. Run fork_fleet_census.py (ghg discipline, actor fork-fleet-census) → census JSON on disk.
  2. Validate the census (--check); on exit 2, stop — sheet untouched, report the stage.
  3. Read the sheet's machine range via the connector; compute the row diff (changed rows, new rows, retirements) against the census + sync run record (for columns M/N).
  4. Write: changed rows via one values batchUpdate (columns A:P only), the column-O verification update, and the Summary tab rewrite — all RAW.
  5. Read back the written ranges; report counts (rows changed / new / retired / unknown) to the lane chat.

Alternative considered and not recommended: a Google service account whose key the script uses directly. It would make the batch a pure script, but it means a standing Google credential stored under the vault rules (write-only, awkward to consume from a script), sharing the sheet to a non-owner identity, and stepping outside the connector — the sanctioned route. It stays documented here as the fallback if a future requirement demands unattended non-agent execution; adopting it is Decision D2's alternative, not the default.

4.3 Failure behaviour and idempotency

  • Partial census: individual compare failures mark only that repo's affected axis unknown (with the error class in column P); the run still writes. A failed mirror compare also forces the develop axis to be interpreted cautiously: the develop compare is independent, so it still publishes — but if the two compares' mirror-head SHAs disagree, the row goes unknown (the §2.1 consistency check).
  • ghg budget denial (exit 75): stop at the stage reached, sheet untouched, report to the lane chat. The census is read-only, so a lost night loses nothing — the next night re-measures everything.
  • Sheet write failure: the census JSON and the computed diff are retained on disk (dated, under the goal's hidden_files) so the next run — or a manual re-run — can apply them; the failure is reported with the stage (read / diff / write / verify).
  • Idempotency: a "change" is any difference in tracked state fields (statuses, counts, SHAs, attribution). Re-running with no state change produces no row writes beyond the column-O verification stamp and the Summary timestamp — and if even those are unchanged in substance, the run reports "no changes" and writes nothing but the Summary run line. Verified-at churn is confined to column O by construction.

7. Risks and mitigations

R1 — False precision: the sheet becomes a polished record of wrong numbers (the orca 0/1,658/258 incident is exactly this failure, pre-sheet). Mitigations: (1) direct compares at census time only — log parsing for figures is forbidden by the schema's design, not by convention; (2) an explicit unknown state with blank counts, plus the cross-compare SHA consistency check, so a measurement problem surfaces as unknown instead of a confident wrong figure; (3) P0 acceptance fixtures and per-figure SHAs (columns G/H/L) make any number auditable to the exact commits it was derived from.
R2 — The batch clobbers human input or fights concurrent edits. Mitigations: (1) writes are confined to machine columns A:P by range — Q:R annotations are outside every write the batch can express; (2) stable alphabetical row order, no batch re-sorts, departed forks retired rather than deleted, and diff-update (not full rewrite) so untouched rows are never rewritten; (3) read-back verification after every write, with the P2 gate explicitly proving a seeded annotation survives.
R3 — Attribution overclaim: "last updated by" reads as if it identifies who changed a branch, when develop changes are largely unattributable. Mitigations: (1) a closed vocabulary (fork-sync / fork-fleet-census / unknown (external change)) — the column can only ever name a bot actor with a run record, or admit ignorance; (2) the column's definition is printed in the Summary tab, and author-inference is explicitly forbidden in the procedure, so the overclaim cannot creep back in as a "helpful" enhancement.
R4 — Gateway budget pressure: the census adds ≈450 ghg calls/night on top of the sync's ≈442. Mitigations: (1) exit-75 discipline — a denied census stops with the sheet untouched and loses nothing (read-only, next night catches up); (2) a distinct actor (fork-fleet-census) so the cost is separately visible in gateway accounting, and the run is placed after the sync in one evening window rather than competing with daytime work; (3) no parallelism and no extra metadata calls beyond the counted set — the fallback branch probe fires only on compare failure.
R5 — Silent staleness: the cron dies or is denied for days and the sheet keeps looking authoritative. Mitigations: (1) the Summary tab carries the census timestamp prominently and every run reports to the lane chat (a missing report is itself a signal, like the sync's); (2) a stated staleness rule — a census timestamp older than 48 hours means the sheet is treated as stale and figures are re-derived live before any decision uses them; (3) the P4 sweep re-point keeps a spot-check of the four vendored forks against live compares, so even the sheet's consumers verify it weekly.
R6 — Scope creep from tracking into acting: a sheet that knows exactly which repos are ff-ready invites the batch to start merging them. Mitigations: (1) the batch is read-only by construction — the script contains no sync, merge, or push calls, and the agent procedure's only writes are to the sheet; (2) forward-merges stay governed by the fleet plan's per-action approvals, unchanged; the sheet informs those decisions, it does not execute them.
