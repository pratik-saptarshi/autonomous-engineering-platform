F-001 Guest memory is balloon-trimmed by the host: ~6.1 GiB of the nominal 7.7 GiB is held by the virtio balloon, leaving an effective guest size of ~1.6 GiB VM environment 2026-11-04

F-001Guest memory is balloon-trimmed by the host hypervisor

Environment Memory Capacity planning

Summary. The virtual machine reports 7.7 GiB of total memory, and free reports roughly 7.2 GiB of it as “used” even when almost nothing is running — yet the resident memory of every guest process combined is only a few hundred megabytes. The difference is not a leak and not any workload: the host’s virtio memory balloon is inflated and holds about 6.1 GiB of the guest’s memory for the hypervisor. The guest’s effective size is therefore about 1.6 GiB, not 7.7 GiB, and the balloon re-inflates after every reboot.

Evidence. Measured live on 2026-11-04 (≈24 minutes after a VM restart, load average 0.45, no agent workloads running):

Total memory/proc/meminfo · MemTotal7.7 GiBThe nominal VM size
Balloon/proc/meminfo · Balloon6.1 GiBHeld by the host via the balloon driver
Balloon driver/sys/bus/virtio/drivers/—virtio_balloon loaded

Page cache/proc/meminfo · Cached~640 MBReclaimable under pressure
Kernel slab/proc/meminfo · Slab~210 MB~40% reclaimable

The guest’s genuine consumption — processes, cache, and kernel structures — totals roughly 1.1 GiB. The same signature (available memory of ~0.4–0.6 GiB with a near-empty process table) was observed on 2026-10-27 and again on 2026-11-01, across multiple VM replacements, which confirms a standing host policy rather than a transient condition.

Diagnostic rule. On this VM, free’s “used” column can never be reconciled against process totals. When memory looks impossibly high, check grep Balloon /proc/meminfo first — the balloon accounts for the gap.

Impact.

  • Heavy work must be sized against ~1.5 GiB effective memory, not the nominal 7.7 GiB.
  • Below roughly 512 MiB free, full test suites fail environmentally — including on a pristine checkout — so suite failures under memory pressure are not, by themselves, evidence of a code defect. Isolated runs are the discriminator.
  • The balloon can in principle deflate and return memory under genuine guest pressure, but in practice it stays inflated in this environment; do not plan on headroom appearing.
  • Long-lived daemons are a real cost in a ~1.6 GiB guest: the NeuroStrata daemon’s idle reaper (shut down after 45 idle minutes) exists for exactly this reason.

Operating guidance.

  • Run full test suites and other heavyweight jobs in isolation; avoid parallel heavy lanes.
  • Judge memory health by MemAvailable and the pressure counters in /proc/pressure/memory, not by free’s used figure.
  • Expect the constraint to reassert itself after every VM reboot or replacement; it is a property of the hosting environment, not of any setup performed inside the guest.
