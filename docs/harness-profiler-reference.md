# harness-profiler reference

## What it is

afurmanov/harness-profiler — a session profiler for Claude Code (Codex is [not supported upstream](https://github.com/afurmanov/harness-profiler#constraints)). It records what the harness itself reports through hooks — every skill, subagent, and tool call — into one JSON line per call, then renders a profiler-style call tree: each **context** (the conversation history a model reads) is a column, nesting follows subagent and forked-skill spawns, and each context carries its token spend. A call tree is the point: the flat hook log says a `validator` ran, the tree says which `implementor` call it checked, whether it ran inline or in a fresh context, and what it cost.

Vendored snapshot: [PROVENANCE.md](../reference/harness-profiler/PROVENANCE.md) — upstream `https://github.com/afurmanov/harness-profiler` (default branch `main`) at `847bd8f6ab2a0348fd7b7057c1943e4c2fa861e8`, the commit `package.json` publishes as **v0.2.2** (2026-11-17, MIT).

## Mapping to the AEP loop

| harness-profiler | AEP (this environment) |
|---|---|
| one record per call, schema `v: 2`, ≤ 4096 bytes, secrets masked at write time | evidence discipline: a trace is a record of what happened, bounded and scrubbed like every other ledger |
| contexts derived from spawn edges, not from guessed timestamps | claims about "which agent did what" ground in the recorded edge, not in a summary |
| token spend attributed per context, from `child_spend` / `SubagentStop.spend` or, when the record carries a transcript path, from the transcript via `spentTokens` | cost claims carry the field they came from; a blank column is shown blank, never estimated |
| vendored snapshot pinned by commit + sha256 manifest | everything imported from upstream is byte-identical and re-vendor-only |

## What AEP uses vs. ignores

**Uses** the pin as a library, from `plugin/libexec/hp.js` (never reimplemented):

- `buildRecord` / `buildEventRecord` — the Claude-shaped payload → record mapping;
- `serialize` — the one-line JSON encoding and its 4096-byte budget;
- `mask` — the write-time secret redaction (three patterns; see the masking caveat below);
- `contextsOf`, `buildForest`, `renderTree`, `renderHtml` — the context-nesting model and both renderers;
- `spentTokens`, `contextSpend`, `fillContextTokens` — the spend arithmetic the columns depend on.

The adoption writes a translator (opencode events → the payload `buildRecord` consumes) rather than a second profiler; the renderer stays the judge of nesting. Phase B and later work consume this tree by relative path.

**Ignores** the Claude Code install path: `.claude-plugin/marketplace.json`, `plugin/hooks/hooks.json`, `plugin/skills/show-profile/`, and `e2e/` (a playwright screenshot run — never installed here, no npm dependency is added). Nothing executes from `reference/`; the snapshot carries the upstream project's own README and design doc as reference data, and those do not govern work in this repository. AEP's `AGENTS.md` does.

The files are named rather than globbed, and checked for existence first, because Node 22+ silently skips a non-matching positional pattern; the step then reads the runner's pass count and fails unless it equals the expected number (45 today), because the file list and `test -f` catch a deleted *file*, never a deleted *test* inside one. ## Caveats carried by the adoption

- The pin is a **Claude Code** profiler. opencode support is the translator's job, and only the five fields the record needs are mapped.
- `mask` covers three patterns; `GITHUB_TOKEN=`, `AWS_SECRET_ACCESS_KEY=`, `client_secret=`, `secretKey=`, `dbPassword=` and `--password x` shapes are among those that pass through. The translator adds one bounded, case-insensitive rule — `CREDENTIAL` in `redactSecrets` (`tools/harness-profile/translate.js`) — and the pin's `mask` then runs on the translated text. The rule matches a key name **containing** `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `CREDENTIAL`, `ACCESS_KEY`/`ACCESS-KEY` or `API_KEY`/`APIKEY`/`API-KEY`, at the start, middle or end of the name and in any case, before `:`/`=` (`GITHUB_TOKEN=`, `AWS_SECRET_ACCESS_KEY=`, `client_secret=`, `secretKey=`, `awsSecretAccessKey=`, `credential=`, `access_key=`, `X-API-Key:`, `x-api-key=`, `api-key=`) or, for a flag, followed by whitespace (`--password x`). The two paired keywords accept a hyphen as well as an underscore (`API[-_]?KEY`, `ACCESS[-_]?KEY`), so the realistic HTTP header shapes redact with their `X-` prefix and key name intact. It keeps the key name and its separator and replaces only the value; a value written as a quoted string (either quote) is replaced whole with the quote character kept, so `GITHUB_TOKEN="a b"` loses both words and a serialized `tool_input` keeps its JSON shape. An opening quote with no closing quote — a truncated tool argument — consumes to the closing quote **or to end of line**, and the span is redacted with only the opening quote restored (`TOKEN="a b` becomes `TOKEN="[redacted]`), so a clipped value cannot fail open. Containment (rather than a suffix or an uppercase env shape) is what restores the mixed-case coverage the three-rule version lost. Structured payloads are covered by key, not text: `redactSecrets` tests each object key against the same name rule before recursing, so `{env:{AWS_SECRET_ACCESS_KEY:…}}`, `{env:{NEUROSTRATA_API_KEY:…}}`, `{headers:{dbPassword:…}}` and `{env:{client_secret:…}}` each have the whole value replaced with `[redacted]` (without descending into it, so an object-valued credential leaves no body), while `{env:{input_tokens:5}}` survives the benign-name skip. Strings remain the text rule's job; the key test handles the structured shapes a real `env`/`headers` argument takes, which contain no `=`/`:` for the text rule to match.
- The keys a profiler exists to report are spared by a callback skip, not by lookarounds: a match whose captured name satisfies `/^(?:(?:input|output|total|num|max|prompt|completion)_?tokens?|tokenizer)$/i` is returned unchanged, so `input_tokens=`, `output_tokens=`, `total_tokens=`, `max_tokens=` and `tokenizer=` survive while `secretKey=` does not. The same whole-name skip guards the object-key test, so `{env:{input_tokens:5}}` survives. The skip is a whole-name test, so any *other* name containing `TOKEN` is still redacted, and these over-redactions are accepted fail-closed by design: `tokens_per_sec=12` loses its value, so do `cache_read_tokens=2048`, `cache_write_tokens=512` and the hyphenated `input-tokens=5` (the skip is underscore-only), and a JSON `{"token":"<id>"}` loses the id. `INPUT_TOKENS=` is spared too — the skip is case-insensitive. Both name runs are bounded (`{0,64}`) and the separator (`[ \t]*`), every value alternative (`[^"\n]*`, `[^'\n]*`, `[^\s"'&,}]+`) and the optional closing quote (`"?`/`'?`, one character, never a nested repeat) keep the whole pattern linear: an unbounded name run on both sides of the alternation backtracks cubically on one long token blob with no separator — 8 KB of repeated `TOKEN` took 14.4 s, and this rule runs inside a capture hook — against ~0.01 ms bounded. The translator's fixtures plant deliberately inert short values (`GITHUB_TOKEN=x1`, `secretKey=abc`, `Authorization: Bearer fakebear`, and the nested `inert1`–`inert4` in `testdata/events/secrets-nested.json`) so they exercise the rule without tripping the `security` job's gitleaks scan — no allowlist entry covers our own fixtures.
- The accepted-redaction list, final: the two load-bearing gaps are **closed** — hyphenated key names (`X-API-Key:`, `x-api-key=`, `api-key=`, `X-ACCESS-KEY:`) and an unterminated quoted value (`TOKEN="a b`, `client_secret='x y`) both lose their value, the latter by consuming to end of line and restoring only the opening quote. One case is **accepted, not fixed**: an object value inside a *string* is clipped at its first `{` (`{"token":{"x":1}}` masks the brace and leaves the object body), because record fields are strings, so the JSONL line stays valid and the tool argument is not reparsed. The structured form of the same value is not clipped: the object-key test replaces the whole value.
- The renderer derives spend from `context_tokens`, `child_spend` / `SubagentStop.spend`, **and** — when a record names a transcript file — the transcript read through `spentTokens` (`hp.js:318-332`). A translator that omits the fields *and* the transcript path renders empty cost columns; the three sources are not interchangeable.

## Retention and fail-closed capture

The capture writes into `.harness-profile/` at the git root (or the directory named by `AEP_HARNESS_PROFILE_DIR`) and bounds that directory on the first event of each process: its own files — `ses_*.jsonl` and `ses_*.parentage.json` — older than **14 days** are removed by modification time, and the directory is held to a **32 MiB** ceiling by deleting the oldest of those files first (`AEP_HARNESS_PROFILE_RETENTION_DAYS` and `AEP_HARNESS_PROFILE_MAX_BYTES` override either bound; `0` disables that bound). A shared explicit directory keeps anything else, including another tool's `*.jsonl`. At the measured ~430 bytes per record and roughly 1 MB/day across four lanes, 14 days is ~14 MB, so the age bound normally binds and the byte ceiling only catches a burst; because pruning runs once per process, growth is bounded **across process starts**, not continuously within one long-lived process. When no git repository is found above the working directory, when `.git` does not resolve to a real git directory, or when the `info/exclude` entry cannot be written and read back, and `AEP_HARNESS_PROFILE_DIR` is unset, capture writes nothing: the trace could not be shown to be excluded from git, so no record is written into an unprotected directory and the handler records a one-time warning naming the reason instead of failing the session. An explicit destination inside a git work tree is held to the same bar: it is written only when that repository's `.gitignore` or common `info/exclude` names it; otherwise capture refuses with a warning naming the directory, the work tree, and both remedies (move it outside the repository, or add an ignore rule). A committed `.gitignore` entry for `.harness-profile/` is the second layer, covering a fresh clone and a runtime write that cannot land. Pruning is the only retention boundary and it is destructive: a trace past either bound is deleted, not archived, and `0` disables that bound rather than emptying the directory (both at `0` means growth is unbounded until an operator removes files).

## Operator doc

Enable/disable (including the service-restart requirement), trace location, retention, refusal
visibility, the masking caveat, and the dev-host scope are documented for operators in the
[harness-profiler operator guide](harness-profiler.md), added in Phase D of the adoption plan
(`docs/superpowers/plans/2026-11-17-harness-profiler-adoption.md`). Capture refusals are recorded
once in `state.warnings` and copied by the plugin to the `opencode serve` log with the
`[aep-harness-profile]` prefix, so an absent trace is diagnosable from the service log rather than
only from this page. The guide also carries the wrapper contract (`scripts/profile-tree.sh`) and the
accepted over-redactions. This page is the pinned-snapshot reference; that page is how to run it.
