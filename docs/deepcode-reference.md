# DeepCode reference

## What it is

HKUDS/DeepCode — DeepCode: Open Agentic Coding: an open agentic coding platform from the University of Hong Kong's Data Science lab (HKUDS). One agent harness serves three clients — a terminal UI, a Desktop app, and a Web app — over a single shared local background service, with goal-driven loop engineering, multi-agent orchestration, and a research line (Paper2Code: research paper → runnable code). Python core with TypeScript Desktop/Web clients and a small Rust component.

Reference snapshot: upstream `https://github.com/HKUDS/DeepCode` at `49805ef25e5c18b2a58ae797028f599b6aca161b` (pinned 2026-10-23, MIT). At pin time: ~16.7k stars, 2,176 forks, 723 commits, 18 releases, actively maintained (last push the day before pinning).

## Why a reference, not a vendor

DeepCode is **not** vendored into this repo and is **not** a component of AEP. It is a competing harness — it overlaps the OpenCode/Muse stack AEP already runs — studied here for three design patterns (below) that map onto open AEP work.

This is deliberately different from the ESF treatment ([esf-reference.md](esf-reference.md)): ESF is small and slow-moving, so it is vendored byte-identical at [reference/esf/](../reference/esf/) with a `PROVENANCE.md`. DeepCode is ~88 MB of repository (Python ~7 MB, TypeScript ~1.2 MB of code) shipping releases roughly weekly; a vendored snapshot would bloat the repo and go stale within weeks. Pinned-commit study only: read upstream at the pinned commit, record what transfers, move on.

## Design study 1: evidence-driven completion

Completion in DeepCode is a protocol, not a model's say-so. Four mechanisms, in `core/agent_runtime/` and `core/verification.py`:

- **Goal closure protocol** (`core/agent_runtime/goal_runtime.py`). Before a Goal-associated Turn may end, a closure prompt forces the model to call `get_goal`, compare the latest objective against the current workspace *and evidence*, then call `update_goal(status="complete")` with "a concise reason grounded in evidence from this Turn" — or `status="blocked"` with an explanation when a persistent external blocker leaves no safe action. The prompt explicitly forbids marking complete "merely because one intermediate check passed." Once the terminal decision is recorded it is durable, and the router strips all side-effecting tools from the model's remaining pass (`visible_tool_names` returns empty): the model gets one final response, no further actions.
- **Operator-supplied evidence command** (`cli/goal_runner.py`, `deepcode loop --test-cmd "<cmd>"`). The command is appended to the objective verbatim as a completion requirement: "User-requested completion evidence: Run `<cmd>` and only mark the Goal complete if it passes." The operator, not the model, picks the proof.
- **Mechanical verification** (`core/verification.py`, driven by `workflows/code_implementation_workflow.py::_verify_generated_code`). After code generation, the workflow runs only *mechanically discovered* test commands from a fixed allowlist — pytest/unittest (chosen by project markers), `npm test` (only if a real test script exists), `cargo test`. Execution is bounded: 300 s timeout, process-group SIGTERM→SIGKILL, output tail-capped at 64 KiB. Each result — `passed`, `exit_code`, `timed_out`, `duration_ms`, bounded stdout/stderr — is written into the workflow's result record. Verification is a deterministic artifact attached to the run.
- **Durable terminal states** (`docs/P2_AGENT_EXECUTION_ARCHITECTURE.md`). Every Turn ends in exactly one of `completed` / `failed` / `interrupted`; a missing `task_complete` event, a provider exception, or an interrupt are all converted to a durable terminal state by an idempotent `_finish()`. A crash mid-Turn is recovered at startup by `recover_incomplete()`, which marks the Turn interrupted — recovery never replays a side effect automatically.
- **The evidence half of loop-breaking** (`core/agent_runtime/evidence_ledger.py`). `EvidenceLedger` fingerprints each tool result (SHA-256 of the normalized result — "the exact content the model read") per canonical call signature. When the same (call, result) pair has come back 3 times, the run *provably* is not making progress — even if the calls were interleaved so no call ever repeats consecutively — and the runner injects an advisory reminder to change approach. Advisory only: it never blocks a call, and it never quotes tool output into the prompt (results are unbounded and may be attacker-controlled).

Honest limit: the complete/blocked decision is still model-mediated, and the evidence command binds through the prompt, not a hard gate. This is weaker than ESF's deterministic gates deciding factory success — see Takeaways.

## Design study 2: permissions and sandbox

Documented in `docs/P1_SECURITY_BASE.md` (mechanism, not decisions: deterministic judgment only, no model, no UI) and extended by the P2 execution architecture. Implementation: `core/harness/permissions.py`, `core/harness/sandbox.py`, `core/harness/env_sanitize.py`, seams in `core/agent_runtime/runner.py`.

- **Three-valued permission engine.** `PermissionEngine.evaluate` is a pure function returning `allow` / `ask` / `deny` before every tool execution. Rules are two-dimensional — tool name × argument pattern (command line or path) — with specificity-first, last-match-wins resolution, so `{"execute_bash": {"git push *": "ask", "*": "allow"}}` behaves as its author expects. Three modes: `default` (mutating tools ask), `plan` (mutating tools denied, read-only exploration only), `full_auto` (rules only, no implicit ask, for unattended workflows), plus a hard blacklist wired into the implementation workflow.
- **Sensitive-path protection beats rules.** A centralized list (`.ssh`, `.aws/credentials`, `.env`, `deepcode_config.json`, `*.pem`, `id_rsa*`, …) is checked *first* and denies regardless of allow rules in legacy, Ask, and Read-only profiles. The only way to lift it is product-level Full Access, explicitly confirmed twice — and that disables the guard *atomically together with* the command sandbox and the workspace write fence, so there is no configuration path that quietly weakens one layer at a time. Ordinary config rules cannot bypass it piecemeal, and even under Full Access, explicit deny rules still take precedence.
- **Frozen at admission.** At Turn admission the configured permissions are normalized into one immutable `ExecutionSecurityProfile`; workers consume that snapshot and never re-read mutable config mid-Turn (`docs/P2_AGENT_EXECUTION_ARCHITECTURE.md`, `docs/AUTOMATION_ARCHITECTURE.md`). Access changes govern newly admitted Turns only. Corollaries stated as invariants: "An Automation cannot raise its own permissions, and a Skill cannot raise permissions either."
- **Fail-closed seams.** A `deny` is returned to the model as a tool result — `Error: permission denied: <reason>` — error-as-data, not a crash or an aborted run. An `ask` with no approval callback (unattended run) defaults to deny with an explanation: autonomy never silently escalates. If the checker or approver throws, the result is deny.
- **Platform sandbox.** `core/harness/sandbox.py` wraps shell/python execution: macOS seatbelt with a generated deny-by-default `.sbpl` (broad reads, writes only inside the workspace + temp, network denied by default, `sandbox-exec` invoked by absolute path against PATH injection); Linux `bwrap` (read-only root bind, read-write workspace bind, fresh `/tmp`, `--unshare-net`); a Windows Job Object backend. Enforcement is tested, not asserted: the suite proves a write inside the workspace succeeds, a write outside is blocked, and a shell attempt to copy credentials out is stopped by the write fence. Degradation is explicit — no backend available means commands run bare but the result is tagged with the backend actually used (`seatbelt` / `bwrap` / `none` / `disabled`), and callers escalate to approval-first. One documented trade-off: the implementation-phase wiring allows network (pip installs) while keeping the filesystem write fence as the high-value layer; `allow_network=False` is available for strict isolation.
- **Credential isolation for child processes.** `core/harness/env_sanitize.py` scrubs credential-shaped variables (`KEY` / `PASSWORD` / `SECRET` / `TOKEN` / `CREDENTIAL` / `AUTH`) from the environment handed to spawned children, and DeepCode's *own* model-connection keys never reach children at all (`DEEPCODE_BASH_FULL_ENV=1` is the explicit opt-out). The stated threat is passive collection, not exotic attack: tool stdout flows into the next outbound prompt, so a single `env` call would forward live credentials to a third-party model relay in plaintext. Forwarding a variable is still possible via explicit `extra_env`, which merges after the scrub — passing a secret becomes a deliberate act.
- **Approvals are durable facts.** Approval requests live in the database (`docs/AUTOMATION_ARCHITECTURE.md`): another application process can approve or deny a suspended Turn, concurrent decisions use compare-and-swap, a cancellation committed first rejects a late approval, and `approved_session` grants persist scoped to the exact Thread and tool name. The local Future is only a wake-up mechanism; the frontend never authorizes anything — the Python backend is the enforcement boundary.

## Design study 3: parallel agents without file collisions

Coordination is by typed resource claims and fenced workspaces, never by inspecting task text (`docs/AUTOMATION_ARCHITECTURE.md` "Execution coordination", `docs/P4_CODE_WORKBENCH_ARCHITECTURE.md`).

- **One coordinator, three claims.** Every Agent and Workflow Turn passes through a single `ExecutionCoordinator`. Admission requires: one slot from the global capacity pool, one Thread fence, and one workspace fence — *either* the canonical-project-workspace fence *or* a managed-worktree fence. Threads sharing the same canonical checkout are therefore serialized; different project workspaces run concurrently; managed worktrees have independent fences. The Desktop registry default is two concurrent Turns across different Threads, and `turn/start` rejects a second active Turn in the same Thread inside the admission transaction.
- **Claims carry identity and epoch.** Each claim records a worker identity and a monotonically increasing Turn epoch; terminal settlement and claim release happen in one transaction, so a stale worker cannot release or complete a successor's claim. Worker death is *proven* with an operating-system file lease before recovery takes ownership — heartbeats alone do not authorize takeover (`core/file_lock.py`, `core/platform_file_lock.py`). A claimed Turn from a proven-dead worker is interrupted, never silently replayed.
- **Managed worktrees.** `WorktreeService` (P4) manages only deterministic sibling directories, each with a dedicated `deepcode/<threadId>` branch and a matching ownership manifest. Thread fork creates an owned worktree so parallel Turns get isolated workspaces. Cleanup validates database ownership, managed path, branch, and manifest together — it never guesses ownership from a directory name — and a dirty worktree requires explicit force; an active Turn or terminal blocks cleanup entirely.
- **Shared-state discipline underneath.** The canonical `SessionStore` JSONL is the single source for Session identity and visible conversation; SQLite Items and the event log are a rebuildable projection. When another DeepCode process has appended visible messages, a runtime reloads that history before its next Turn rather than writing over it. File edits inside the workbench additionally use optimistic SHA-256 revisions: a stale view cannot overwrite newer content.

## AEP takeaways

- **Per-task evidence.** Adopt the closure shape, keep AEP's stricter verdict: a completion claim should have to cite evidence produced during the run, and mechanical verification should be allowlist-discovered, bounded, and recorded in the run artifact — the pattern ESF (deterministic gates) and DeepCode (`core/verification.py`) converge on. DeepCode's model-mediated complete/blocked call is the part *not* to copy as-is; pair its closure protocol with a deterministic gate that can veto.
- **Boot-gate / permissions work.** The frozen `ExecutionSecurityProfile` is the transferable idea for issue-tracked boot-gate work: resolve permissions once at admission, snapshot them immutably, and never let a worker re-read mutable config mid-run. Add the two ordering rules: sensitive-path deny is evaluated before any allow rule, and an unanswered `ask` in an unattended lane is a deny, not a pass.
- **Credential hygiene for build lanes.** `env_sanitize.py`'s reasoning applies verbatim to AEP's cron and build lanes — tool output flows into prompts here too. Scrub credential-shaped names by default; make forwarding a secret an explicit, visible act.
- **Parallel-lane coordination.** AEP's overnight-parallel-lanes already isolates by worktree. DeepCode adds the claim discipline around it: a fence per workspace, a monotonic epoch per claim, settlement-and-release in one transaction, and OS-lease proof of worker death before another lane takes over. Worth adopting before lane counts grow.
