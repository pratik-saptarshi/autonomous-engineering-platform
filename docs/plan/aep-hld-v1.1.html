1. Purpose and scope

This document consolidates the design decisions reached in the working discussion into one reference: how the Autonomous Engineering Platform (AEP) is built and deployed portably, and how it governs two kinds of autonomous execution — fast local ralph-loop lanes and sandboxed ESF (Engineering Software Factory) pipelines — on a shared set of core services.

It is a design, not a record of finished work. Section 9 states exactly what exists in the repository today and what is still to be built; reading the rest of the document as "already implemented" would be wrong.

3. Goals and non-goals

Goals

  • One-command install and run on Linux (x86_64 and ARM64), the Muse 8 GB VM, and macOS (Intel and Apple Silicon).
  • Many parallel lanes under one governance plane with bounded, predictable resource use.
  • Deterministic verification decides success; an agent saying "done" never does.
  • Fail closed: no autonomous run starts if the environment is unfit.

Non-goals (v1.1)

  • Native Windows binaries or service wrappers.
  • macOS guest VM images (macOS runs the native binary under launchd).
  • Replacing beads or NeuroStrata.
  • Modifying the vendored reference/esf tree (it changes only by re-vendoring).

6. Resource model (12 CPU / 48 GB / 220 GB)

ResourceTotalSubstrateTier 1Tier 2
vCPU122 reserved4–6 shared4–6 priority
RAM48 GB8 GB16 GB24 GB
Disk220 GB30 GB (models, DB)70 GB (worktrees, caches)120 GB (microVM images, artifacts)
Capacity is memory-bound, not count-bound. Six Tier-2 pipelines at 4 GB fit the 24 GB budget; six at 6 GB do not (36 GB). The "4–6 pipelines" and "8–10 lanes" figures are therefore ceilings under typical sizing, not guarantees. The design enforces this with admission control that reserves memory per lane before start (LLD §6), rather than a fixed lane count. Per-lane footprints are estimates from capacity reasoning; they have not been benchmarked on this machine, and no container runtime is currently installed on the host to measure with.

Reference sizing for other targets: the Muse 8 GB VM runs the substrate plus at most 2 lanes (AEP_MAX_LANES=2, 384 MiB floor, ONNX threads 2); Tier 2 is not expected on Muse.

8. Dispatch and lifecycle

  1. Intake. Work is a beads issue carrying a tier tag (local or factory) and acceptance criteria.
  2. Preflight. aep boot must pass: binaries, NeuroStrata answering, standing guards present, policy blob matches HEAD, memory floor met.
  3. Admission. Dispatcher reserves RAM/CPU for the lane against the profile budget; if it cannot, the task waits (bounded) rather than oversubscribing.
  4. Execute. Tier 1: claim worktree, start lane container, run plan/TDD/review/verify. Tier 2: submit factory run with workflow ID esf-beads-<ID>.
  5. Verify. Both lanes emit SHA-256 receipts. ESF patches are applied in a clean Tier-1 lane and re-verified before any PR.
  6. Close. PR merges, bd close, learnings inscribed to NeuroStrata, lane and reservation released.

9. Governance invariants

  • No lane starts unless aep boot passes (fail closed).
  • All GitHub traffic from lanes goes through ghg.
  • policy.data must equal the committed blob; lanes run with credential-named env vars scrubbed.
  • ESF refuses to run with hardening.acknowledge_open_egress = true in a governed deployment (the upstream default for a fresh factory init is true, so AEP must assert the opposite).
  • Model tiering: ralph lanes at standard/measured; frontier/thorough reserved for factory runs.
  • A task has exactly one ledger identity (the beads ID) across both lanes.

10. Implementation status (as of this document)

Built in develop

  • cmd/aep with version, info, boot, verify, supervisor, lock-test.
  • internal/platform/{memory,lock,process} for Linux, macOS and Windows; internal/verifier/runner (allowlist discovery, tail-capped output, SHA-256 receipts, memory preflight, budgets).
  • Makefile targets binaries, vm, oci; scripts/package-vm.sh, scripts/package-oci.sh; Containerfile, docker-compose.yml.
  • Root CI runs gofmt, go vet, go test.

Not yet built

  • aep boot today checks only the memory floor and platform; the NeuroStrata/guard/gh-auth/policy checks still live in scripts/boot-gate.sh.
  • aep supervisor today runs boot gate + one verification pass per tick; it does not dispatch lanes or ESF runs.
  • Lane coordination remains in scripts/lane-coord.sh (Linux flock); no Go lane manager, no admission control, no beads adapter, no dispatcher, no ESF client, no Colima profile or compose topology for the substrate.
  • The "unified verifier inside the CubeSandbox template" and NeuroStrata hooks in the ESF harness are design intent only.

12. Review status

The v1 → v1.1 review applied the paperthin lenses (hate, ssotize, modelchk, factchk, debloat) as a single-author pass. It surfaced the dispatch-stall root objection, the dual-ledger drift risk and the egress-default fact. It was not an independent multi-reviewer panel, and its "full approval" wording should be read as "no remaining objections from that pass". An independent adversarial run should precede production activation, and it should specifically attack the nested-virtualization assumption above.
