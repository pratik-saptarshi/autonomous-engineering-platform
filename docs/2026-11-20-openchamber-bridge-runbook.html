OpenCode–OpenChamber bridge — runbook

Runbook · 2026-11-20 · OpenCode–OpenChamber lane · Companion to the OpenChamber Hybrid Scoping document (2026-11-20), which is the plan of record. Bridge built and smoke-tested 2026-11-20; pilot staged, awaiting the next replay-core wave.

Executive takeaway

A lane dispatches a bounded worker task by writing a brief file and running one command: dispatch.py wakes/checks the OpenCode background service, creates a titled session in the task's worktree, sends the brief (plus a standard footer) as the prompt over the service API, polls until the session goes idle, and harvests the report file into the SDD workspace with a ledger entry carrying session id, tokens, cost, wall-clock, and before/after git state. Never opencode run — it hangs in this VM; the API route is the only route. If anything stalls or fails, the fallback is the existing one: re-dispatch the task to a Muse subagent under the direct-drive rules. The bridge changes where execution is visible, not who holds authority: Muse stays the control plane (briefs, memory, ghg-gated publishing, censuses, gate re-runs), and merge decisions stay Pratik's, per PR.

All API calls go through the opencode api CLI, which attaches the service credentials itself. The dispatcher never reads the service password file, and no credential appears in the ledger, the archived brief, or any report.

Paths and environment — OPENCHAMBER_BRIDGE_HOME

The kit separates kit-internal files from the runtime data home. dispatch.py, brief-footer.txt, and brief-template.md always resolve relative to the dispatcher script itself. The runtime data home — where the dispatch ledger (ledger.jsonl) is written — is the path variable OPENCHAMBER_BRIDGE_HOME, resolved in this order:

  1. An explicit --ledger argument wins over everything.
  2. $OPENCHAMBER_BRIDGE_HOME when set — the VM's setup initialization exports it (see tools/openchamber-bridge/env.sh, sourced from ~/.bashrc); in the current VM it points at the live executing home in the AEP goal workspace.
  3. Fallback: the directory containing dispatch.py — correct whenever the executing copy itself lives in the data home.

Consequence: the repo copy of the kit is self-contained (its seeded ledger sits beside the script), while the live dispatcher keeps appending to the executing ledger regardless of which copy a session invokes.

2. How a lane dispatches a task

Step 1 — write the brief

Write the brief exactly as for a Muse subagent today: the finding/charge quoted verbatim (grep-verified against its source), red-first instructions where charged, stop conditions, and the gate commands the worker must run in the worktree. Do not repeat the footer content — the dispatcher appends brief-footer.txt, which carries: the mandatory report path, the report format, the no-push / no-post / worktree-only / no-deletion rules, the public-hygiene rule, and the environment block (PATH, GOTMPDIR=$HOME/.gotmp, sequential builds, ~1.5 GiB effective memory). The adapted brief is archived next to the report as <report>.brief.md.

Step 2 — pick the title

Title convention, so the OpenChamber board reads as a work board with no UI changes:

  • Reviews: <repo> PR<n> · W<wave> re-review · <base7>..<head7> — e.g. replay-core PR7 · W7 re-review · 4008a19..a1b2c3d
  • Implementers: <repo> PR<n> · W<wave> implement · <finding shortname>
  • Panelists: <repo> PR<n> · W<wave> panel · <lens>

The session's location.directory is the worktree, so the board groups by project correctly.

Step 3 — dispatch

python3 tools/openchamber-bridge/dispatch.py \
  --brief    <brief-file> \
  --workdir  <scratch-or-feature-worktree> \
  --title    "replay-core PR7 · W7 re-review · 4008a19..a1b2c3d" \
  --report   <SDD-workspace>/wave7-rereview-report.md \
  --model    opencode-go/deepseek-v4.1-flash \
  --timeout 3600 --stall-seconds 600 --poll-seconds 15
ArgumentMeaning
--briefBrief file; its text (plus footer) becomes the prompt.
--workdirSession location.directory. Reviews use a scratch worktree at the head commit; the main tree is never a session workdir for review work.
--reportThe contract path, inside the lane's SDD workspace. Substituted into the footer.
--modelprovider/model-id (default opencode-go/deepseek-v4.1-flash). Allowlist — Pratik's standing rule, 2026-11-20, expanded 2026-11-21: ONLY these models may be dispatched on the bridge — opencode-go/deepseek-v4.1-flash, opencode-go/glm-5.3-flash, opencode-go/minimax-m3.1-flash, opencode-go/muse-spark-1.3-contributor, opencode-go/hy4-flash-free, opencode-go/iceman-contributor-free, opencode-go/longcat-2.5-free, opencode-go/beam-free, and opencode/tidepool-alpha-free (Tidepool is listed only under the opencode provider — no opencode-go variant exists). The dispatcher enforces this and refuses any other model (exit 64) before any session is created. Within the allowlist, keep the pilot rule: a different model family from the implementer under review.
--ledgerOptional: append the dispatch record to a specific SDD ledger instead of the bridge ledger.
--timeout / --stall-secondsOverall poll budget, and the no-progress window that declares a stall (see §5).

At dispatch, record in the SDD ledger — the same entry a Muse subagent dispatch gets today — the session id, title, model, base commit, and expected report path. The dispatcher's own ledger line carries all of these plus tokens/cost and the worktree git HEAD + dirty-file count before and after (local only, no network).

Step 4 — what the dispatcher does

  1. Health/wake: GET /api/session — this call is itself the documented wake route; the dispatcher retries it three times with backoff before giving up (exit 2).
  2. Create: POST /api/session with title, location.directory, model {id, providerID}, agent build.
  3. Prompt: POST /api/session/<id>/prompt with {text} — the adapted brief.
  4. Poll: session record + message list every --poll-seconds until an idle marker lands, the stall window trips, or the timeout expires.
  5. Harvest: §3. Then append the ledger line and print the full dispatch record as JSON on stdout.

3. Report harvesting into the SDD workspace

  • The report file remains the contract. When the session goes idle, the dispatcher verifies the file at --report exists and is at least --min-report-bytes (default 100). A passing harvest sets report_authored: true in the ledger.
  • If the session ended without a report file (or a trivial one), the harvester extracts the final assistant message into the report path, prefixed with a HARVESTED-NOT-AUTHORED marker, sets report_authored: false, and exits 5. The controller treats that task as UNREPORTED — chase or re-dispatch it exactly as a Muse child that finished without reporting.
  • Token counts, cost, and outcome come from the session record into the ledger line — per-task cost data the lane does not have for Muse subagents today.
  • The transcript is the backup, never the deliverable: open the session in OpenChamber (or GET /api/session/<id>/message) to audit what the worker actually did — reds, gate runs, file edits — against its report's claims.
  • Gate discipline is unchanged: a worker's green is a claim; the controller re-runs the gate first-hand in the main tree before anything is published.

4. Lifecycle and wake procedure

SituationProcedure
Normal dispatchNothing to start by hand. The dispatcher's health/wake call wakes the OpenCode service if it is stopped; session history persists on disk across service restarts.
OpenChamber board downBring it up from the OpenChamber Space's Bring up control, or ~/workspace/repo-evals/openchamber-trial/run.sh. Check GET http://127.0.0.1:3411/health → openCodeRunning: true. The board is visibility only — a dispatch works without it, it just isn't visible until the board is back.
After a VM replacementProcesses do not survive; everything on disk does (trial stack, ~/.local/state/opencode/, session history). Recovery is the two steps above: any opencode api call (the dispatcher does it) + Bring up. A session interrupted mid-task leaves its transcript up to the interruption and its worktree exactly as the worker left it; the SDD ledger + git log in the worktree are the recovery source of truth.
StoppingThe Space's Stop control stops OpenChamber only and deliberately leaves the OpenCode service running. The dispatcher never stops the service either. There is no step in this runbook that stops the service.
MCP taxPer-service-start, not per-session: rea connects (~7.5 s); the neurostrata MCP times out (~34 s) while its daemon is down — the standing state. Starting that daemon is Pratik's call and is not part of this bridge. The pilot measures the tax inside its wall-clock budget.

5. Failure modes, exit codes, and the fallback

ExitMeaningController action
0Session completed, outcome succeeded, report authored.Normal path: verify claims, re-run the gate first-hand, proceed.
2Health/wake or session creation failed.Check the service (opencode api GET /api/session by hand); if it will not wake, fall back (below).
3Stall declared — no new message and no session update for --stall-seconds. Partial transcript harvested.Direct-drive stall rule, verbatim: the partial work is assessed from the worktree + transcript, and the task is re-dispatched — to a Muse subagent by default.
4Overall timeout. Partial transcript harvested.As for a stall.
5Session completed but report missing/trivial; harvested fallback written, marked not-authored.Treat as UNREPORTED: chase once via a follow-up prompt only if the transcript shows the work was done; otherwise re-dispatch.
6Session outcome failed/interrupted, or the prompt was rejected.Read the transcript tail for the failure, then re-dispatch.

Fallback to a Muse subagent. Any exit other than 0 — or a pilot success-criterion failure on a live wave — re-dispatches the same brief (minus the footer; Muse subagents get the standing brief discipline directly) to a Muse subagent under the existing direct-drive execution rules. The bridge is an execution plane, not a dependency: a wave never blocks on it. Record the fallback and its reason in the SDD ledger and, during the pilot, in the pilot report.

  • Session dies mid-task (VM replacement, service crash): exposure is identical to a Muse subagent dying — work product is files and commits in the worktree. The ledger holds the session id, so the partial transcript stays findable.
  • VM memory pressure (~1.5 GiB effective): one OpenCode worker at a time, sequential builds — the same discipline as the lane's current one-implementer rule.
  • Plausible-but-wrong report: the standing defenses, unchanged — fresh independent re-review, controller-side gate re-run, and (pilot only) dual verification against ground truth.

The no-push rule is detective, not preventive — stated plainly

Sessions run with the user's filesystem and shell access. The no-push / no-post rules are brief instructions in the footer, not a sandbox — exactly as they already are for Muse subagents. The controls are detective: ghg accounting surfaces any GitHub API call, the dispatcher records the worktree's git state before and after, and the controller diffs the remote ref before and after every dispatch (the pilot script does the before leg). A violation ends the experiment for that task class. Keeping all publishing on the Muse side — pushes, thread replies, PR posts, through ghg, with ref verification — is what makes this acceptable. No session ever receives a deletion task; the deletion rule (explicit confirmation + 1-hour delay + reconfirmation, exact targets) is unchanged.

7. The pilot — staged and ready

Subject: the next replay-core re-review (PR #7, next wave), dispatched the moment its brief arrives from the replay-core lane under Pratik's wave authorization. Everything below is staged in …/openchamber-bridge/pilot/ so the pilot is a dispatch, not a build:

  • brief-template.md — the re-review brief with slots for wave, base..head, scratch worktree, model, report path, and the verbatim charge; the controller grep-verifies the charge against its source before dispatch.
  • run-pilot.sh — the parameterized dispatch (title built from the convention; pre-dispatch remote-ref record for the no-push check). It refuses to run until PILOT_AUTHORIZED and every slot are set from the real brief.
  • success-criteria.md — the scoping document §5 criteria, all must hold: verdict matches ground truth under pilot-only dual verification; every removed/changed test line accounted for; report lands complete at the SDD path without controller edits; zero rule violations (ref diff + ghg ledger); wall-clock within 2× the ~15–20 min Muse-side baseline, wake and MCP taxes included; tokens recorded either way. Judged on quality of reds first, wall-clock second, tokens third.

After the pilot run, the controller writes the pilot report (HTML, in this files/ directory): session id, model family vs the implementer's, wall-clock vs baseline, tokens/cost, dual-verification result per finding, each criterion PASS/FAIL with evidence, any stall/fallback events, and a verdict recommendation for Pratik's adoption decisions — adopt per task class or not; re-reviews only or implementers too; model-pairing policy; whether the dispatcher graduates to a maintained lane tool or stays pilot-grade.

8. What does not change

  • Publishing authority — Muse side, through ghg, per-action as today. Sessions never push or post.
  • Merge authorization — Pratik's per-PR call, never bundled into a wave authorization.
  • Memory — NeuroStrata primacy; inscription is the controller's job as work closes. Sessions neither read nor write lane memory.
  • Hygiene — the public-tree scrub and the replay-core public-hygiene rule apply to session-produced diffs exactly as to any other diff, checked Muse-side before publish.
  • No new UI, no config changes, no scheduling — the title convention makes the existing OpenChamber board readable as-is; dispatches are controller-initiated only.

The pilot closed on 2026-11-20 with all five criteria PASS. The bridge has since run in production-shaped use; this section records the operating state as of 2026-11-23.

  • Current versions (verified live 2026-11-23): OpenCode v2.4.1 (upgraded from v2.3.0 via opencode upgrade; OpenCode Go still connected) and OpenChamber 2.8.0 (upgraded from 2.7.3 via npm install @openchamber/web@2.8.0 in the trial app dir; /health reports openCodeRunning: true, isOpenCodeReady: true against the background service). The version figures in sections 6–7 are the pilot-era record and are kept as written.
  • Dispatches since the pilot: scoped re-reviews of AEP PR #191 (five rounds, ending CLEAN) and of the replay-core PR #7 fix waves; two adversarial panels under the roundtable protocol (replay-core at its Phase-2 merge; AEP develop as shipped state) — both judged SOUND WITH CONDITIONS; a third panel on the replay-core PR #11 Sourcery round-2 findings (F1/F2/F3 verified as in-model defects, F4 ruled out-of-model under the settlement caller contract); and re-reviews of the resulting fix wave and of a single-commit Codex repair, both ACCEPTED. The model allowlist and the different-family reviewer rule remain in force; one allowlisted model (muse-spark-1.3-contributor) has since debuted as a panel seat.
  • Scratch-worktree placement rule (standing, learned 2026-11-23): a dispatched session's scratch worktrees go only under ~/workspace/worktrees/, never inside the repository checkout under review — tree-walking checks in the target repo (gofmt scans, file-count floors, phase gates) treat anything inside the checkout as product, and a session's probe file inside the tree failed a gate run on an otherwise clean head. Briefs must name the worktree location explicitly.
  • Ledger: the ledger.jsonl in this repo is a three-entry pilot-era seed by design. The live ledger is runtime data under the bridge home (OPENCHAMBER_BRIDGE_HOME) and is not mirrored here.
  • Kit currency: dispatch.py, brief-footer.txt, and env.sh in this repo were verified byte-identical to the live executing copies on 2026-11-23.
