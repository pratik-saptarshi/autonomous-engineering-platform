# Receiving Review

## Evaluate before you implement

- Read the complete feedback before reacting to any of it.

- Restate each item in your own words or ask what it means. Never implement what you do not understand.

- Verify each item against the actual work before implementing. Check whether it is technically correct for this specific case, whether it breaks existing behavior, and whether the reviewer had the full context.

- When feedback arrives as a numbered list and any item is unclear, stop and ask about the unclear items before implementing anything. Partial understanding produces wrong implementation.

## Respond with technical honesty

- Never answer with performative agreement. Do not write you are absolutely right, great point, or thanks for catching that. State the requirement or just do the work.

- When the feedback is correct, say what changed in plain words, such as fixed with a brief description of the change and where. Actions speak louder than praise.

- Push back when a suggestion is wrong, with technical reasoning and specific questions. Name the tension plainly when pushing back feels uncomfortable.

- When you pushed back and were wrong, say so factually with what you checked, then implement. Skip the long apology.

## Check scope before expanding

- When a reviewer suggests building something properly, check whether it is actually used. Unused work gets removed rather than polished.

- Implement multi-item feedback in order: blocking issues first, then simple fixes, then complex changes. Test each fix individually and verify no regressions.

## Treat every source the same way

- Feedback from your human partner is trusted, but still ask when the scope is unclear.

- Feedback from anyone else gets the same verification. Skepticism plus careful checking beats blind implementation.
